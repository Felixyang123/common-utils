# CS 模式采用"可用性优先"的配置模型

**上下文**：CS 模式下客户端线程池配置可由 admin-server 集中下发。问题是：配置服务端在客户端启动那一刻不可达时该如何表现。

**决策**：采用可用性优先模型。客户端本地 `thread.pool.pools[]` 作为**启动引导兜底**先在本地建池（保证不差于 LOCAL 模式），同时推送给服务端；服务端配置随后通过首拉/长轮询**覆盖**本地。客户端声明初始值并可在每次启动重推，但**不覆盖**服务端被运维调过的值（服务端为运行期权威）；服务端不可达时退化到本地配置仍可运行。

**被否的替代**：服务端为唯一事实源——首拉失败即池缺失或启动失败（强一致优先）。否决理由：线程池是运行时基础设施，配置中心抖动不应让业务线程池消失；此处可用性的价值高于配置强一致。

**后果**：客户端本地 `pools[]` 同时承担"初始声明值"与"服务端不可达时的兜底地板"双重语义。运维在服务端的调优具有运行期权威，客户端重启不会回滚它（依赖 add 的"存在即返回、不覆盖"语义——见 [[CONTEXT]] 配置所有权）。
