四、发现并修复的缺陷

两处均为重构前就已存在的真实生产缺陷——旧的 Controller 单测使用 mock 存储，无法触达校验逻辑；新增的真实存储 E2E 测试将其暴露。修复位于 service/ApiKeyAdminService.java。

BUG-1 updateApiKey 会清空 API Key 凭证哈希

现象：仅更新名称/描述的 PUT 请求，会新建一个不含 apiKeyHash 的 ApiKey 对象 → 存储层抛 ValidationException，接口返回业务码 400；即便不抛异常，也会把真实凭证哈希覆盖为 null。

修复前
ApiKey apiKey = new ApiKey(); apiKey.setAppId(appId); apiKey.setAppName(request.getAppName()); // 未设置 apiKeyHash / createTime apiKeyStorage.saveApiKey(apiKey); // → 400
修复后
ApiKey existing = storage.getApiKey(appId) .orElseThrow(...); ApiKey updated = ApiKey.builder() .apiKeyHash(existing.getApiKeyHash()) // 保留凭证 .createTime(existing.getCreateTime()) // 保留创建时间 .appName(request.getAppName())...build();

BUG-2 删除 API Key 后变更历史不可读

现象：getHistory 以 apiKeyStorage.exists() 为前置校验，导致 Key 删除后，其 DELETE 审计记录永远返回业务码 404 而无法读取。

修复前
if (!apiKeyStorage.exists(appId)) { throw new ConfigNotFoundException(...); // → 404 } return historyStorage.getHistory(appId);
修复后
// 审计日志与 Key 当前是否存在解耦， // 删除后仍可读到 DELETE 记录， // 未知 appId 时历史存储返回空列表 return historyStorage.getHistory(appId);
