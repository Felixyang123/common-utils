# 缓存降级防护体系

## Status

accepted

## Context

`common-cache` 定位为**加速层**（数据库是权威数据源），采用 L1（本地）+ L2(Redis）多级缓存 + Redis Pub/Sub 跨节点失效同步。企业级评审暴露了三个会致命的故障模式：

- **缓存雪崩**:Redis 不可用或冷启动时，大量不同 key 同时 miss，流量集体涌向共享 DB，把核心业务的 DB 资源耗尽（棕断）。
- **缓存击穿**:热点 key 失效瞬间，并发请求争抢回源，造成对同一 key 的重复加载。
- **L1 永久脏**:Pub/Sub 是 fire-and-forget，订阅断连/消息丢失后 L1 脏数据无兜底；叠加 `Cache.get()` 不检查过期，脏数据可能永久驻留。

DB 与其他核心业务**共享**，因此缓存重建流量必须有爆炸半径上限，不能把 DB 吞吐打满。

## Decision

采用**三层降级防护 + serve-stale 语义 + L1 TTL 兜底**:

1. **单飞（single-flight)**：按 key 合并并发回源，修复原实现"拿不到锁返回 null"的缺陷，改为等待在飞结果并共享返回值。
2. **并发舱壁（concurrency bulkhead)**：本地 `Semaphore` 限制同时在飞的回源查询数（≤ DB 连接池容量），防止连接池耗尽。常开，不依赖故障检测。
3. **速率限流（token bucket)**：本地 Guava 令牌桶，给缓存重建流量划定**持续吞吐量上限**，保护共享 DB 上的核心业务流量。

**关键语义与约束**:

- **本地实现**:Redis 版限流器在"Redis 不可用"这一核心降级场景下同样失效（循环依赖），故三层全部用 JVM 内实现。
- **检查顺序**:`token.tryAcquire()`（非阻塞）先于 `bulkhead.tryAcquire(有界超时)`；**绝不持有舱壁 permit 去等待 token**（浪费稀缺并发）。
- **拒绝语义 = serve-stale 优先**：任一层拒绝时，只要存在过期旧值就返回旧值；无旧值才被界等待，最终失败抛专用 `CacheDegradedException`（带 category/key，暴露指标），而非静默返回 null。仅"既无缓存又被限流"的请求失败。
- **量纲区分**：舱壁限并发（保护连接池/防线程堆积），token 限速率（保护 DB CPU/IO)；两者经利特尔法则（并发数 ÷ 平均延迟 = 吞吐）配套调参。
- **L1 一致性兜底**：修复 `Cache.get()` 过期检查后，给 L1 设独立短 TTL，使"丢消息导致的 L1 脏数据"最长存活时间有明确上界（最终一致，窗口 = TTL)。

同步通道维持**单通道广播**（节点规模小、category 有限枚举），配合 `RedisMessageListenerContainer` 自动重连与 L1 TTL 兜底，不引入分通道/消息中间件。

## Considered Options

- **用 Redis 版限流器做降级限流**：拒绝——核心降级场景（Redis 宕）下自身不可用，循环依赖。
- **砍掉 token 桶只留舱壁**：拒绝——舱壁只防连接池耗尽（崩溃），不防 DB CPU 被打满饿死共享的核心业务（棕断）；token 桶用于流量隔离。
- **主动对账（消息序号 / 定期 L1↔L2 比对）**：暂缓——当前节点规模小、category 有限，TTL 兜底已把"永久脏"压缩为有界窗口；对账会引入对账线程与业务线程同步消息的并发复杂度。留作未来增强。

## Consequences

- 调参一致性负担：舱壁并发数与 token 速率需按利特尔法则配套调，调错则 belt-and-suspenders 反而互相干扰。
- serve-stale 意味着限流期间业务可能读到**过期但存在**的数据；已对全部 category 接受该语义。
